# Formal Foundations of Verifiable AI Assurance

**「AIが実行してよいと判断した」を、「どの条件を満たすから採用できるか、第三者が確かめられる」へ。**

本リポジトリは、既存の認証・セキュリティ・運用基盤が持つ証拠を、**業務上の許可条件と、実行後の監査で確認する事項に結び付ける形式化ソース**です。新しい情報が必要な場合と、情報は既にあるが適切な検証が必要な場合を分け、既存公開のCyber Assurance GatewayとResponsibility OSに数学的に接続します。

出発点は「3製品を導入すべき」という結論ではありません。外部の要求から目標を定め、**足りる情報・足りない情報・正しい検証・履歴に残すべき区別**を、反例と証明の両側から扱います。公開物は基礎理論であり、製品や接続アダプターではありません。

**検証状態：本配布版のLeanビルド・公理監査は未実行です。** 検証済みとは表示していません。対象ソースの検証方法と、成功判定の条件は第6節に記載しています。

## 1. 協業で加えられるもの

**既存の証拠を集めるだけでなく、「その証拠と検証結果が、顧客のどの要求を支えるか」を、再検査できる論理条件にすること**が、この研究の用途です。

例えばAIが業務操作を提案した場合、認証情報や監視結果があることだけでなく、その操作を認める権限、許される変更範囲、監査に残す事項との対応を説明する必要があります。本ソースでは、外部から決める書込み・削除の許可範囲を、既存公開Gatewayの許可条件と結び付け、実行に関する前提が成立した場合の方針充足を定理として記述しています。さらに、既存公開の記録が保持する区別をResponsibility OSの履歴ポリシーへ接続しています。［2］［4］［5］

| 既存基盤を生かす部分 | 本成果が提供する形式的な判断根拠 |
|---|---|
| 認証・監視・既存ログ・外部照会 | 利用可能な全情報を含め、必要な区別が既に得られる場合も正当に評価する。 |
| 既存情報を用いた業務判断 | 情報が足りることと、その情報を扱う検証が正しいことを分ける。同じ情報でも不適切な判定と適切な判定があり得ることを具体化する。 |
| 業務上の許可条件 | 外部の許可範囲と公開Gatewayの契約条件を接続し、結論を前提に置かずに、選定した資源ポリシーの充足を導く。 |
| 顧客への説明・監査 | 公開記録のどの区別を、有限履歴にも保持できるかを明示する。単なる「成功」ラベルに置き換えない。 |

共同サービスで検討する価値は、**「安全そうだという説明」から、「採用した条件・証拠・検証結果の対応を提示できる保証」への拡張**です。この理論だけで、導入効果、独立検証器の実装品質、第三者運用、費用削減や性能を実証したとはしません。特定企業の既存機能の不足や、当社技術の不可欠性を前提にもしていません。

## 2. 要求の根拠を、証明の都合から独立させる

情報の真正性・実行の保証・責任の追跡可能性は、以下の異なる確認事項を整理する見出しです。一次資料がこの3分類の完全性・唯一性や、当社製品の必要性を認定したという意味ではありません。

| 外部の根拠 | そこから採る確認事項 | この形式化の範囲 |
|---|---|---|
| W3C VC Data Model v2.0 §1.1・§2［1］ | 証明書の検証可能性と、内容の真実性・利用側の業務判断を区別する。 | 署名や発行元の確認から、業務条件の成立へ飛躍しない。暗号実装や記載内容の真実性は証明しない。 |
| RFC 9334 §8.2［3］ | 健全な端末であることと、その企業が接続を許可する端末であることは別である。 | 同文書の所有条件を含む例を、独立した方針・観測・判定式に分けて具体化する。 |
| NIST SP 800-53 Rev.5 AC-3［2］ | 適用ポリシーに従った論理アクセス認可を実施する。 | モデル内の権限と、外部が定める書込み・削除の許可範囲を対象にする。AC-3全体への適合証明ではない。 |
| 同AU-3・AU-9［2］ | 監査で必要な内容を記録し、監査情報を保護する。 | 選んだ記録上の区別の保持を扱う。全項目の充足、ログの改ざん耐性、保存期間、法的責任の確定は別の義務である。 |

### 外部例を、実際に一般定理へ接続する

RFC 9334 §8.2は、同じメーカーの健全な端末であっても、企業が所有していなければネットワーク接続を許したくない場合を説明しています。［3］ 本ソースの `RFC9334` 名前空間は、その例から**「健全であり、かつ自社所有である」**という選定方針を定め、2つの事実の真偽4組をすべて扱います。

| 健全性 | 自社所有 | 選定方針 | 健全性だけの判定 | 方針に対応する判定 |
|---|---|---|---|---|
| いいえ | いいえ | 不許可 | 不許可 | 不許可 |
| いいえ | はい | 不許可 | 不許可 | 不許可 |
| はい | いいえ | 不許可 | **誤って許可** | 不許可 |
| はい | はい | 許可 | 許可 | 許可 |

ここでは、次の3つを別々の結果として記述しています。

**情報が不足する場合。** 健全性しか観測できなければ、下の2行を区別できません。一般定理 `Requirements.insufficient_iff_conflict` を実際に適用し、`RFC9334.health_only_is_insufficient` を得ます。

**情報は足りるが、判定が不適切な場合。** 健全性と所有の両方が手元にあるのに、健全性しか確認しない判定は誤受入を起こします。`health_only_check_on_full_evidence_is_unsound` と `policy_check_exact` は、**同じ入力情報に対する、不適切な判定と方針どおりの判定**を分けます。判定式は、先に定めた方針との一致を全4組について調べるもので、任意の成功フラグを正しさと定義したものではありません。

**既存機能で既に足りる場合。** 所有情報を既存基盤から得られるなら、その能力を利用できます。`existing_ownership_information_is_enough` は、追加ベンダーや新しい情報源を要求しません。また、適切な再計算が新しい情報源ではないことと、その再計算が正しい判断に役立つことは両立します。

この4組は、3領域の必須性を示すために作った旧4事例とは別です。外部文書に示された方針の真理値を網羅した**説明用の意味モデル**であり、実在製品の構成や実測結果ではありません。メーカーは固定し、健全性・所有の値を事実として扱っています。それらを正しい証拠から取得する義務を、この例だけで満たしたことにはしません。

## 3. 公開Gatewayから業務条件・監査へつなぐ

### 業務条件は、検証結果とは別に与える

対象は、既存公開Gatewayが定義する操作と状態です。利用側は、**書込みを許可する資源と削除を許可する資源を、実行結果を見る前に決める**ものとします。要求は「操作主体に権限があり、モデル内の実際の書込み・削除が許可範囲内にあること」です。外部送信・権限昇格など別種の効果まで、この選定ポリシーの結論に含めるものではありません。

`PublicGateway.published_allow_core_respects_external_resource_policy` の論理は次のとおりです。

**公開Gatewayの許可条件 `AllowCore` が成立 → 操作主体の権限と、効果の保守的な上限が成立 → その上限が利用側の許可範囲に含まれ、対象実行が公開操作モデルと一致するなら → 実際のモデル内効果も許可範囲内。**

単に「要求を満たす実行なら、要求を満たす」と置いたものではありません。入力は公開契約・上限と方針の包含関係・実行との対応です。結論の `ExternalResourcePolicy` は、外部から決めた許可範囲と実際のモデル内効果を照合する別の述語です。

| 前提 | 具体的に何を確認するか | ソースでの扱い |
|---|---|---|
| `AllowCore` | 公開モデルの権限・効果上限・承認等の条件が成立する。 | 固定した既存公開定義をそのまま使用。AIの許可ラベルや署名だけから成立させない。 |
| `writeBound`・`deleteBound` | 効果上限が、利用側が先に定めた許可範囲に収まる。 | 上限から外部方針への対応として明示。実際の効果の方針充足そのものは仮定しない。 |
| `Sem` | 対象の操作・事前状態・事後状態が、公開操作モデルの関係を満たす。 | 理論と実行を結ぶ前提として明示。任意の実機が満たすとはしない。 |

**成立例も同じ公開範囲にあります。** `published_read_example_satisfies_allow_core` と `published_read_example_satisfies_external_policy` は、既存Gatewayの公開済み読取り例を再利用し、書込み・削除を一切許さない方針で、許可条件と要求が両立することを記述します。新しい実装例ではなく、論理上の空虚さを避ける確認です。

逆方向の `external_policy_violation_excludes_allow_core` は、対応する前提の下で、方針に反するモデル内実行が同じ許可条件を満たせないことを述べます。**これは論理上の排除であり、実機で迂回経路を遮断したとの実証ではありません。**

### 記録を「成功」の一語に潰さない

`published_record_preserves_selected_audit_history` は、既存の `ADIC.EvidenceRecord` を観測する場合に、そこにある主体・操作・対象・方針版・結果の区別を、Responsibility OSの `PreservesPolicy` に接続します。数学上の有限履歴での保持であり、新しい記録形式ではありません。

`published_record_is_sufficient_for_selected_record_questions` と `published_record_questions_preserve_history` は、同じ公開記録の型を、一般理論の `FamilySufficient` と履歴定理へ実際に代入しています。**一般定理とGatewayを別々に置いただけではありません。** 対象には不成立候補も含め、検証済み事例だけに絞って要求が自明に真になる構成にはしていません。

ここで保持するのは記録上の区別です。主体の記載が現実の本人と一致すること、記録が欠落・改ざんされていないこと、AU-3の時刻・場所等を含む全項目がそろうことまで、この射影だけで証明するものではありません。

### 既存定理の入力を省略しない

従来の `published_commit_yields_execution_evidence` も残しています。ただし、その入力 `CommittedByLedger` には、記録の関係だけでなく `Sem` や効果上限内であること等も含まれています。したがって「台帳に成功と書かれているだけで、実行の正しさが導かれる」とは説明しません。上の資源ポリシー定理は、この `CommittedByLedger` を前提にしていません。

## 4. 前提を現実へ適用する基準

外部資料は要求の根拠になりますが、特定環境で前提が成立することまでは代わりに証明しません。適用時には、以下を対象業務の証拠で確認します。

| 項目 | 満たすべき条件 |
|---|---|
| 要求 | 顧客・業務・監査側が先に決める。実装が判定しやすい内容に差し替えない。 |
| 対象範囲 | 運用条件・脅威モデルの下で成立し得る状況を含む。観測済みの標本一覧に限定しない。 |
| 全観測 | 判断時点で利用できる認証、ログ、照会結果等を含む。既存製品の情報を省いて不足を作らない。 |
| 検証の正しさ | 情報が存在するだけでなく、採用する判定が、その情報と両立する状況で要求を満たすことを確認する。 |
| 実行・記録との対応 | 同じ操作・同じ対象状態について前提を対応付ける。実装の迂回防止、証拠の真正性・鮮度、ログの完全性は別途確認する。 |

**一意なIDを付けただけでは、保証の根拠になりません。** 観測済みの各行に別IDがあるだけなら、数学上は事例を区別できてしまいます。対象には、同じIDや同じ証拠と両立する別の状態も含める必要があります。`EvidenceScope.same_identifier_can_leave_a_conflict` は、同じ対象の代替状態に関するこの問題を具体化します。2つの実在端末が同時に同じ一意IDを持つと仮定するものではありません。

`checked_compatible_evidence_is_sound` は、受け入れた証拠と両立する全事例で要求が成立し、実際の事例もその範囲に含まれるなら、受入が健全になると述べます。実際の事例をモデルから落としたり、検証器の正しさを未確認のまま置いたりすることを正当化しません。

モデル間の移行について、`sufficiency_transfers_with_faithful_abstraction` が置く観測・要求の対応は、結論を移すための**十分条件**です。あらゆる固定目標についての必要条件だとは主張しません。逆に、反例を実環境へ移す `realized_conflict_transfers` では、実際に成立し得る事例と、その判断者の全情報でも両者を区別できないことが要ります。

## 5. 主要な形式化

以下はすべて `VerifiableAIAssurance` 名前空間です。必要十分性は、固定した対象範囲・保証目標・観測についての情報条件であり、計算可能性や処理性能の保証ではありません。

| 識別子 | 内容 |
|---|---|
| `sufficient_iff_exact_judge` | 正確な判定が存在するための必要十分な情報条件。 |
| `Requirements.sound_useful_at_iff_no_bad_collision` | 特定の正常事例を誤受入なしで受け入れられる条件。「全拒否」を有用な解答としない。 |
| `Requirements.joint_sufficient_iff_resolves_conflicts` | 追加情報が残る全ての必要な区別を補う条件。一部の成功例だけでは十分としない。 |
| `Requirements.reconstructible_addition_is_redundant` | 再計算と新しい情報源を区別する。再計算の実務的価値を否定する定理ではない。 |
| `RFC9334.policy_check_exact` | 外部文書に基づく選定方針と判定式を、全真理値について対応させる。 |
| `RFC9334.health_only_check_on_full_evidence_is_unsound` | 入力に情報がそろっていても、不適切な判定は誤受入を起こす。 |
| `PublicGateway.published_allow_core_respects_external_resource_policy` | 既存公開の許可条件を、外部で定める資源ポリシーへ接続する。 |
| `PublicGateway.published_read_example_satisfies_external_policy` | 公開済みの読取り例による、方針充足の非空な成立例。 |
| `PublicGateway.published_record_questions_preserve_history` | 公開記録を一般的な要件群・責任OSの履歴保持へ接続する。 |
| `EvidenceScope.same_identifier_can_leave_a_conflict` | IDによる標本の識別と、証拠による事実の判別を区別する。 |

旧 `Independence` の4事例は、可能性の例示・回帰検査として残しています。**現実の3領域の独立性や必須性の根拠には使いません。** 新しい一般定理、RFCの例、Gatewayとの接続は、この旧4事例に依存していません。基本的な情報・論理原理について、世界初や特定企業の独占的な数学原理とも主張していません。
